3. RAW を dbt の入力として名前付けする：source YAML と Staging SQL

_sample_app__sources.yml

models/staging/sample_app/_sample_app__sources.yml

RAW テーブルの「dbt 内で使う名前」と、実際の Databricks 上の所在地を結び付けます。

version: 2

sources:
  - name: sample_app
    database: test_catalog
    schema: raw
    tables:
      - name: dbt_test_customers
        description: 顧客マスタ（RAW）
      - name: dbt_test_orders
        description: 注文データ（RAW）

ここで定義した source 名とテーブル名を、 SQL 側の source('…', '…') で完全一致させます。

stg_sample_app__dbt_test_customers.sql

models/staging/sample_app/stg_sample_app__dbt_test_customers.sql
select
  customer_id,
  customer_name,
  email,
  created_at
from {{ source(
  'sample_app',
  'dbt_test_customers'
) }}

上の色付き部分は _sample_app__sources.yml と対応します。
この SQL ファイル自身は dbt モデル名：stg_sample_app__dbt_test_customers になります。

stg_sample_app__dbt_test_orders.sql

models/staging/sample_app/stg_sample_app__dbt_test_orders.sql
select
  order_id,
  customer_id,
  order_date,
  amount
from {{ source(
  'sample_app',

この SQL ファイルも staging/ 配下なので、 dbt_project.yml の設定により test_catalog.staging の View として作られます。

4. Staging モデルの説明・テスト：SQL ファイル名と YAML の name を結ぶ

_sample_app__models.yml

models/staging/sample_app/_sample_app__models.yml

モデルの説明、各列の説明、品質テストを定義します。ここでの name は SQL ファイル名（拡張子なし）と一致させます。

version: 2

models:
  - name: stg_sample_app__dbt_test_customers
    description: 顧客マスタの staging モデル
    columns:
      - name: customer_id
        data_tests:
          - unique
          - not_null

  - name: stg_sample_app__dbt_test_orders
    description: 注文データの staging モデル
    columns:
      - name: order_id
        data_tests:
          - unique
          - not_null
ファイル名 ↔ YAML の name
stg_sample_app__dbt_test_customers.sql → 拡張子を除く → stg_sample_app__dbt_test_customers
この一致により、説明・列定義・unique / not_null テストが対象 SQL モデルに付与されます。

select
  c.customer_id,
  c.customer_name,
  c.email,
  count(o.order_id) as order_count,
  coalesce(sum(o.amount), 0) as total_amount,
  min(o.order_date) as first_order_date,
  max(o.order_date) as last_order_date

from {{ ref('stg_sample_app__dbt_test_customers') }} c

ref() 内の名前は、参照先の SQL ファイル名から .sql を除いた dbt モデル名です。 dbt はこの記述から「Staging を先に作り、その後 Mart を作る」と判断します。 このファイルは marts/ 配下なので、Table として作成されます。

7. 命名上の「厳格な一致」と「チーム慣習」

対象判定理由
dbt_project.yml厳格dbt のプロジェクト設定ファイルとして必要。
SQL ファイル名（拡張子なし）と YAML の models[].name実質的に厳格説明・テストを対象モデルに紐付けるため。
source('source名', 'テーブル名') と source YAML の名前厳格名前が一致しないと dbt が Source を見つけられないため。
ref('モデル名') と参照先モデル名厳格名前が一致しないと dbt が参照先モデルを見つけられないため。
stg_ / mart_ / __慣習dbt の予約構文ではない。用途・ソース・業務領域を人間が読みやすくするための規約。
YAML の先頭の _慣習補助定義ファイルであることを示す目印。YAML は dbt に読み込まれる。
