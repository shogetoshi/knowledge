データメッシュの核心

所有は分散したい、しかし横断では繋ぎたい——この緊張を「最小の共有解釈」で解く

本資料はデータメッシュ（Zhamak Dehghani, 2019）の考え方を、「共有する解釈を最小にする」という一本の論理として再構成したもの。原典は4つの原則を並列に提示しており、この「核」の読み方は原典に反しないが、本資料独自の整理である。
全体の流れ
  1. 問い — 中央集約はなぜ限界になるのか
  2. 核 — 分散したい、でも繋ぎたい。答えは「最小の共有解釈」
  3. 仕組み① データプロダクト — 「使える」を保証する境界
  4. 仕組み② グローバルID — 「繋がる」を保証する最小の共有
  5. 仕組み③ 連邦ガバナンスと自動執行 — 合意を回し続ける機構
  6. 実務への着地 — 既存データレイクからの移行
1. 問い

中央集約はなぜ限界になるのか

「データはまず一箇所（レイク/DWH）に集め、中央チームが整えて配る」——この方式は小〜中規模では有効だが、組織が大きくなると構造的に破綻する。

  1. 中央データチームがボトルネックになる — 取込・意味の問い合わせ・修正・ダッシュボード作成の依頼が全部中央に集中する
  2. データの意味を一番知っている人が管理していない — 中央は基盤に詳しくても業務の意味には詳しくない。「データはあるが正しく使えるか分からない」状態に
  3. データレイクが「データ沼（Data Swamp）」になる — 誰が作ったか・どれが正か・使ってよいのか分からないテーブルの山
具体例：「売上」の意味が複数ある問題

「売上」という項目ひとつでも、受注/出荷/請求ベース、キャンセル控除の前後、税込/税抜、会計上/KPI上——と意味が複数ある。この判断ができるのは業務ドメインの人間であって、パイプラインを運用する中央チームではない。

一方で、中央集約には決定的な利点があった。全部が同じ場所にあるから、ドメイン横断の分析が容易だということ。だから「じゃあ分散させよう」と単純にはいかない。分散した瞬間、この利点が消えてサイロ化するからである。ここに本質的な緊張がある。

比較表：中央集約型が向く場合・破綻する場合
観点中央集約（レイク/DWH中心）限界が来る条件
主役中央データチーム利用者・ドメイン数の増加で依頼が飽和
意味の管理中央が頑張って整理業務の複雑化で追いつかなくなる
横断分析容易（同じDWHで結合）—（これが失いたくない利点）
向く規模小〜中規模・単一事業大規模・複数事業・複数ドメイン
2. 核

分散したい、でも繋ぎたい——答えは「最小の共有解釈」

整理すると、両端はどちらも失敗する。

完全な中央集約完全な分権
何が起きるか中央が全データの意味を解釈する「全社正規モデル」「ゴールデンレコード」を目指す各ドメインが勝手にデータを持つ
結末委員会で決めるうちに陳腐化。単一モデルはどの文脈にも合わない。中央が承認の関所＝ボトルネックにID体系がバラバラで結合不能。分析者ごとに数字が違う。サイロ化
データメッシュの答え：共有する解釈を最小にする。ただし改訂可能な形で。
属性・状態・分類は共有しない——各ドメインが自分の文脈で決める。
全社で共有するのは「同じ実体を指差せる」という同一性の一点だけ。
そしてその合意すら「絶対の真理」ではなく、履歴付きで改訂できる合意として管理する。

共有解釈がゼロだとドメイン間の結合は原理的に不可能なので、横断利用と無解釈は両立しない。設計問題は「共有する解釈をどこまで薄くできるか」であり、データメッシュは相互運用が買える最小の射影を選んだ思想だと言える。

具体例：なぜゴールデンレコード（最大の共有解釈）は詰むのか

山田太郎さんが3システムに別々に存在し、妻・花子さんのカードで支払っているとする。

CRM:      C-1001  山田太郎
EC会員DB:  M-555   taro@example.com
請求:      B-88    支払者=山田花子

中央MDMが「唯一の正しい顧客」を1行に統合しようとすると：

golden_idnamepayerこの注文の顧客は？
GR-1太郎? 花子?花子???

会計にとっての正解は「花子（請求主体）」、CSは「太郎（利用者）」、マーケは「山田家（世帯）」。1行のゴールデンレコードはどれかにとって必ず間違いになる。しかも統合方針を決める会議に数ヶ月かかり、全ドメインが待たされる。

4原則は、この一点を成立させる装置として読める

原則この物語での役割
① ドメインごとのデータ所有分権の宣言——意味の決定権を、意味を知る現場に返す
② Data as a Product「使える」の保証——分権しても他者が使える品質・契約で公開する（→仕組み①）
③ セルフサービス基盤自動執行の場——合意を人手でなく基盤が守らせる（→仕組み③）
④ フェデレーテッドガバナンス最小合意の維持機構——何を共有するかをドメイン代表の合議で決める（→仕組み②③）

以降、この「最小の共有解釈で繋ぐ」を実現する3つの仕組みを順に見る。

3. 仕組み①

データプロダクト — 「使える」を保証する境界

意味の決定権をドメインに返すと言っても、ドメインがデータを抱え込んだらサイロである。そこでデータメッシュにおける所有（オーナーシップ）は、囲い込む権限ではなく公開する責任として定義される。

データプロダクト ＝ データの「公開API」。
内部データ（Raw・中間テーブル）は閉じてよい。その代わり、外部利用向けに
定義・品質SLO・スキーマ・変更ポリシー・アクセス条件を明示した契約付きのデータを公開する義務を負う。

内部と公開の境界を先に引いておく

レイヤー内容アクセス
Raw / 業務システム由来生データ（内部実装）ドメイン内＋最小限の基盤・監査のみ
ドメイン内整備済み中間・クレンジング済み（内部実装）基本ドメイン内
公開データプロダクト契約付きの外部向けデータ他ドメインが権限・契約に基づき利用

この境界があると、外部からの要求に原則で答えられる。公開プロダクト（製品）は使ってよい。未公開の内部データ（設計図）への要求は「内部実装なので原則不可」と打ち返せる——「製品が売られているんだから設計図も見せろ」には応じない、ということ。毎回悩む代わりに、プロダクト設計時点で先に悩んでおく。

具体例：同じ注文データの公開レベル分けと、要求への打ち返し 
order_raw               生データ。注文ドメイン内部のみ（PII含む）
order_fact_restricted   詳細明細。許可された分析者向け
order_fact_public       標準分析用。PII除外・疑似化ID
order_summary_daily     日次集計。広く利用可能
「注文データを分析したい」
  → order_fact_public を使ってください

「order_raw を見たい」
  → 原則不可です。不足項目があれば
     データプロダクト改善要望として受け付けます

ソフトウェアの「公開APIは使ってよいが、内部DBへの直接アクセスは不可」と同じ規律。

「断る権利」は「改善要望に応える義務」とセットで初めて成立する。改善ルートにリソースやSLAが割かれないと、探索的分析やML開発が止まり、ドメインが新しいボトルネックになる。探索フェーズには期限付き・目的限定の例外アクセスを機動的に出せる運用も必要。

横断的な集約も「目的別のプロダクト」として作る

横断ニーズを持つ利用側ドメイン（consumer-aligned domain）——経営分析、マーケ分析など——が、各ドメインの公開プロダクトを入力に、自分の目的に合わせた集約プロダクトを作りオーナーになる。「あらゆる用途に効く万能の customer_360」を中央に1つ作る発想には慎重で、集約もあくまで目的別・オーナー付きで扱う。

具体例：公開プロダクトを組み合わせた横断分析SQL

キャンペーン別の初回購入とLTV。接触ログは顧客×キャンペーンで1行に集約してから結合し（重複計上防止）、LTVの起点は接触時点に置く。

WITH first_touch AS (
  SELECT customer_gid, campaign_id,
         MIN(touch_timestamp) AS touched_at
  FROM marketing.campaign_touch
  GROUP BY customer_gid, campaign_id
)
SELECT
  t.campaign_id,
  COUNT(DISTINCT t.customer_gid) AS touched_customers,
  COUNT(DISTINCT o.customer_gid) AS purchased_customers,
  SUM(o.net_sales)               AS revenue_90d
FROM first_touch t
LEFT JOIN orders.order_fact o
  ON o.customer_gid = t.customer_gid
 AND o.order_timestamp BETWEEN t.touched_at
                           AND t.touched_at + INTERVAL '90 days'
GROUP BY t.campaign_id;

net_sales の意味は注文ドメインが、campaign_id はマーケドメインが契約として保証している。複数キャンペーン接触時の収益配分（アトリビューション）は別途、共通定義としてガバナンス対象になる。

ここで問題が残る。プロダクト化は「使える」を保証するが、ドメインごとに顧客の定義がバラバラなら「繋がる」は保証されない。それを担うのが次の仕組みである。

4. 仕組み②

グローバルID — 「繋がる」を保証する最小の共有

polyseme：モデルは共有しない、IDだけ共有する

「顧客」「商品」のように複数ドメインに登場する概念を polyseme（多義概念） と呼ぶ。各ドメインは自分の文脈での「顧客」を自分でモデリングしてよい（DDDの境界づけられたコンテキスト）。単一の正解モデルは作らず、polyseme にグローバルID（gid）を割り当て、ドメイン間はそのIDで結び付ける。

横断分析に必要なのは「全ドメインが同じ顧客モデルを使うこと」ではなく、
「どのドメインの顧客ビューも、同じgidを指差せること」。
具体例：山田家のデータで見る全体像

全社で持つのは薄いID読み替え表だけ（属性は持たない）：

source_systemsource_idcustomer_gid
CRMC-1001G-001（太郎）
ECM-555G-001（太郎）
BILLINGB-88G-002（花子）

各ドメインは自分の定義で顧客ビューを公開する——3つとも「顧客」の定義が違うが、それでよい：

customer.customer_profile   顧客＝EC会員      (G-001, active, 2025-04-01)
finance.billing_view        顧客＝請求主体    (BE-88, payer=G-002, users=[G-001])
marketing.household_view    顧客＝世帯        (H-10, members=[G-001, G-002])

横断分析はgid経由で成立する：

orders.order_fact:  O-1  buyer=G-001  12,000円
                    O-2  buyer=G-002   3,000円

マーケの世帯LTV : H-10のメンバー[G-001,G-002]の注文合算 → 15,000円
会計の請求先集計: BE-88に紐づく注文を集計          → 別の正しい数字

どちらも正しく、矛盾しない。ゴールデンレコードで1つの答えに統合していたら、どちらかが必ず間違った数字を見ることになる。

読み替えテーブルの正体：「IDの変換」と「同一性の全社合意」

データ構造としてはただのID読み替え表である。そして「だけ」であることが意図的な設計——従来MDMは読み替え表＋統合属性（ゴールデンレコード）まで作ろうとして属性の正で詰んだ。データメッシュは読み替えの部分だけを全社資産として残し、属性はドメインに返した。

ただし各行は「C-1001とM-555は同一人物である」という業務上の主張（判断結果）である。だからこの主張は絶対の真理ではなく、改訂可能な合意として管理する——マージ/分割の履歴、確信度、判断者を記録し、誤りが分かれば履歴付きで訂正する。

具体例：mappingテーブルのカラム設計と、守るべき原則

守るべきは「カラム数」ではなく「同一性の解決以外の情報を入れない」こと。名前・住所・ステータスを1つでも入れた瞬間、ゴールデンレコードへ滑り落ち始める。運用メタデータは入れてよい：

カラム用途
source_system, source_id, customer_gid本体
statusactive / merged
match_method, confidenceemail_exact 等、なぜ紐づいたか
valid_from, valid_toいつ時点の対応か
decided_by自動 or スチュワード判断

マージ履歴は別テーブル：

old_gidnew_gidmerged_atdecided_by
G-003G-0012026-07-01顧客ドメイン スチュワード

マージ後も旧gidは履歴経由で解決可能に保つ。gidは「不変」ではないが「追跡可能」。

具体例：初回構築の手順 —「先に名寄せ、あとに採番」

「全レコードにIDを振ってから統合」ではなく、「名寄せしてクラスタ化 → クラスタ1つにつきgidを1個採番」。マージは下流全体に影響する高コストイベントなので、構築時には極力発生させない。

① 各ドメインから候補レコードを収集（source_id + email/電話/氏名）
② マッチングルールでクラスタ化
     email完全一致          → 同一
     phone+姓一致           → 確信度が閾値未満なら人手確認キューへ
③ クラスタごとに gid を採番（gidに意味を持たせない）

運用開始後は増分処理：新レコード → 既存と照合 → 一致なら紐づけ / 不一致なら新規採番 / グレーは仮採番してキューへ。マージは運用後の例外イベントとして履歴付きで扱う。

gid自体も「一つの射影」であることを認める

「G-xxx＝一人の人間」と決めること自体が一つの解釈である。データメッシュはこれを否定しない。避けたいのは「共有解釈の存在」ではなく「最大化された共有解釈」であり、gidは相互運用が買える最小の射影を、改訂可能な形で持つという選択である。

したがって「人」という粒度は特権的ではない。person（G-001）・世帯（H-10）・請求主体（BE-88）はすでに3つの射影が並存している状態であり、必要なら「自然人＋法人」を束ねるParty型のID空間も作れる。

gidは「実体があるから振る」のではなく、
「複数ドメインがこの軸で結合・集計したいという実需と合意があるから振る」。
gid体系＝全社で共有する視点のカタログ。無闇に増やさない。

新しいgid体系を作ってよい条件：その軸で結合したい利用者が複数ドメインに実在する／「何をもって同一とするか」に関係ドメインが合意できる／マッピング維持・マージ伝播のコストを払う価値がある——の3つが揃ったとき。

具体例：Partyモデル（自然人＋法人）と、並列ID空間のルール

銀行・保険等では「Party＝自然人または法人」として契約主体を統一的に扱う。判断基準は「その抽象で相互運用が実際に買えるか」——未回収残高やKYCが個人・法人をまたぐなら効く。ただしマッチングルール（個人：email・電話／法人：法人番号・登記）や規制は型ごとに分かれるため、「ID空間は1つ、名寄せ運用は型別」となる。

person_gid と party_gid を並列で持つのはOK。ただし条件が1つ：同一性の判断は1回だけ行い、片方を導出にする。

person_registry   G-001 = 山田太郎   ← 名寄せの主権はここ
org_registry      O-055 = 株式会社X

party_registry（導出層）
  PT-001 → person G-001
  PT-055 → org    O-055

NG: 2つのレジストリが独立に名寄せを実行する——いずれ判断が食い違い、「どちらのIDで結合するかで数字が変わる」状態が再発する。判断は一箇所、IDは複数ビュー。

また「山田太郎は株式会社Xの担当者」は統合ではなく関係テーブル（PT-001 —is_contact_of→ PT-055）で表す。実体と関係を混ぜない。

gidの使い方：書くのは自由、寄りかかるのは禁止

場面ルール
自分が発生源の実体のPKgid使用禁止。subscription_id 等は自前採番
業務フロー経由で他ドメインを参照上流のローカルID（ec_member_id 等）を優先保存。gidは公開時に解決
入力が公開プロダクトしかない場合gid参照OK（それが結合キー）。ただしマージ履歴への追随義務を引き受ける
公開データプロダクトgidを必ず載せる（相互運用標準）。公開時にmappingを引いて付与すればマージに自動追随

要するに、gidの安定性に業務処理を依存させないこと。gidは改訂されうる値であり、保存する側が履歴に追随する責任を持つ。

5. 仕組み③

連邦ガバナンスと自動執行 — 合意を回し続ける機構

最小の共有解釈は、決めて終わりではなく回し続けるものである。誰が決め、誰が実行し、人はどこに登場するのか。

決める主体と範囲：連邦制で、最小限だけ

グローバルID標準や相互運用ルールを決めるのは、中央の専任組織ではなくドメイン代表の合議体（フェデレーテッドガバナンス）。決める範囲は横断利用に必要な最小限に絞る。

連邦ガバナンスで決める最小限の全社標準各ドメインが持つ
gid標準（採番・一意性・再利用禁止）
発生源ドメインの登録義務
相互運用ルール（公開プロダクトはgidを載せる・変更通知）
参照コード（国・通貨等）
マージ履歴の管理義務		 自分の文脈での概念モデル（「顧客とは何か」）
属性の意味・業務定義
名寄せルールの中身（業務判断）
グレーゾーンの裁定（スチュワード）
品質責任・プロダクト提供

「email一致なら同一人物か」「家族カードの支払者は別人か」という名寄せルールの中身はほぼすべて業務判断なので、そのエンティティのオーナードメインが決める。連邦が決めるのは形式と義務だけ。

実行は会議ではなく基盤：computational governance

合意はレビュー会や承認フローで守らせるのではなく、可能な限り基盤に埋め込んで自動執行する（policy as code）。人が登場するのは例外の裁定だけ。

具体例：新規顧客が追加されたとき、何が自動で起きるか

設計原則：業務フローを絶対にブロックしない・全部非同期・中央から他ドメインのテーブルには書き込まない。

① 発生源ドメイン（EC）
   M-999 が INSERT（レジストリが落ちていても登録は成功する）
    └→ 非同期イベント発行:
       { source: "EC/M-999",
         match_attrs: { email, phone, name } }

② 中央レジストリ（プラットフォーム運用・全自動）
   1. 受入検証（必須マッチング属性がなければ隔離キュー）
   2. マッチング（決定的ルール → 確率的ルール）
   3. 3分岐:
      ├ 高確信度で一致 → 既存gidに紐づけ
      ├ 一致なし       → 新規gid採番
      └ グレーゾーン   → 仮gidを即発行し、スチュワードキューへ
   4. mapping書込（method, confidence, decided_by=auto）
   5. イベント発行: { event:"gid_assigned", gid:"G-104", is_new:true }

③ 発生源ドメイン
   次回の公開パイプラインで gid が付与され、プロダクトに現れる

④ 他ドメイン
   原則、何も起きない（それが正しい設計）

工夫は2つ。冪等性（リトライで同じイベントが2回来ても結果が同じ）と、グレーゾーンでも仮gidを即発行して下流を止めないこと（誤りは後でマージイベントとして訂正＝結果整合性）。

具体例：他ドメインに発生する義務 / 自動化チェックリスト
立場やること
公開プロダクトの利用者作業ゼロ。上流の次回リフレッシュで新顧客が見える
gidキーの派生データ保持者新規gidは対応不要。gid_mergedイベントの購読だけ必須（保存済みgidの付け替え）

自動化すべきもの：受入契約の検証／マッチング・採番（冪等）／イベント発行（gid_assigned / gid_merged / gid_split）／グレーゾーンのキュー投入／公開時のgid解決（プラットフォームがAPI/ライブラリ提供）／公開プロダクトのCIゲート（gidカラムの参照整合性チェック、違反は公開ブロック）／マッチ率・キュー滞留の監視。

責任分担：

役割担当
新規レコードの供給発生源の各ドメイン（義務）
マッチング・採番の基盤プラットフォームチーム
ルール（形式・義務・履歴）連邦ガバナンス
グレーゾーン・マージの判断エンティティのオーナードメイン
実務の落としどころ：レガシーのID体系がバラバラな組織では「グローバルIDへの合意」自体が大仕事になるため、薄い中央MDMサービスや「ID権威としてのドメイン」を置くハイブリッドに落ち着くことが多い。その場合も中央のスコープはID・マッピング基盤・照合ルールの枠組みに限定し、属性の中身や業務の意味決定まで吸い上げないこと。そこまで寄せると、壊そうとした中央ボトルネックを名前を変えて再建することになる。
6. 着地

実務への着地 — 既存データレイクからの移行

既存レイクは解体しない。共有プラットフォームとして残し、データセットごとの所有権だけを 業務ドメインに「再ラベリング」していく。レイクは「アーキテクチャの主役」から 「各ドメインのプロダクトをホストする基盤の一つ」へ役割を降りる。「メッシュの1ドメイン」にはしない。

移行ステップ

  1. 棚卸し — 「このテーブル、誰のもの？」に答えられる状態にする
  2. 分類 — A: 特定ドメインのもの / B: 横断統合物 / C: 中間データ / D: 所有者不明
  3. Aは業務ドメインへオーナー移管（最初はBusiness Ownerだけドメイン、技術は中央でも可）
  4. Bは利用側ドメインの集約プロダクトへ、Cは内部実装として非公開に、Dは廃止候補に
  5. 横断需要の高い1〜2ドメイン（顧客×注文×商品など）でパイロット
  6. 運用主体を「中央主導 → 共同運用 → ドメイン主体」と段階的に移す

中央データチームは「全データを集めて依頼に応えるチーム」から、「カタログ・権限・品質監視・レジストリ・CI/CDを提供し、ドメインのプロダクト化を支援するプラットフォームチーム」へ役割を変える。役割の細分化は禁物で、Ownerは1ドメインに1つ、関係者は複数（内部分担はRACIで）。

具体例：所有権の再ラベリングとプロダクト定義 
lake.raw_customers  → Owner: 顧客ドメイン   ← 物理は動かさない
lake.raw_orders     → Owner: 注文ドメイン
lake.customer_ltv   → Owner: 顧客分析ドメイン
Data Product: order_fact
Owner:        注文ドメイン（連絡先: #data-order）
Join Keys:    order_id, customer_gid, product_id
Metrics:      gross_sales, net_sales
Quality:      order_id not null / duplicate = 0 / net_sales >= 0
Change Policy: 破壊的変更は30日前通知

新しいドメインを設計するときの注意

内部テーブル公開データプロダクト
PKは自前のローカルID（gid禁止）
名寄せ材料（email・上流ID）を入口で必ず取る
他ドメイン参照はマッピング可能なIDで（野良ID禁止）
新概念のIDは自分で採番してよい（gid化は実需が出てから）		 gidは公開時に解決して載せる
利用者向けに設計（内部のダンプにしない）
他ドメインの属性を焼き込まない（影のマスタ化防止）
タイムスタンプ・valid_from/toを最初から設計

既存の顧客・製品を「参照するだけ」なら独自採番もレジストリ登録も不要。登録義務が発生するのは、自前の会員登録口など新しい識別子の発生源になる場合だけ。可能な限り自前採番を避けて既存のマッピング可能なIDを持ち回るのが安上がり。

全体を一言でまとめると

データレイクは「データをどこに集めるか」の話。データメッシュは「意味の決定権を現場に返しながら、どうやって繋がり続けるか」の話。

核は一点：「中央がすべてを解釈する」と「何も共有せずサイロ化する」の間で、
改訂可能で最小の共有解釈——グローバルID——に留めること。

データプロダクトが「使える」を保証し、gidが「繋がる」を保証し、
連邦ガバナンス＋自動執行が、その合意を回し続ける。
ドメインは意味を所有し、公開の義務を負う。人が裁くのは例外だけ。
物理基盤は共有してよい——共有をやめるのは「解釈」であって「インフラ」ではない。
